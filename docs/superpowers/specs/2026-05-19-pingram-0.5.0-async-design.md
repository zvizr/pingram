# Pingram 0.5.0 — Async Mode Design

**Status:** Approved for implementation
**Target version:** 0.5.0
**Previous release:** 0.4.0 (2026-05-19, this same day)

---

## Context

Pingram 0.4.0 shipped retry + typed errors + CI on top of a sync-only public API. The README's Roadmap promised async mode as the next item and it is the highest-leverage feature still outstanding: it unlocks `asyncio.gather`, FastAPI integration, and Jupyter usage that the sync client cannot serve cleanly. Async is also the planned headline for the next r/Python Showcase Saturday + HN moment that was deliberately held back from the 0.4.0 release.

## Goals

1. Ship an `AsyncPingram` class that mirrors the sync `Pingram` surface 1:1, with `await` semantics on every public method.
2. Reuse the 0.4.0 retry policy and typed exception hierarchy without duplication of intent — only mechanical duplication of the executor body.
3. Maintain 100% backward compatibility — `pip install -U pingram` from 0.4.0 must produce identical behaviour for existing sync callers. No constructor changes, no error type changes, no return type changes for `Pingram`.
4. Land async coverage in CI on every PR via `pytest-asyncio` + `respx` (which already supports async transparently).
5. Set up the release for a credible Reddit/HN announcement: the headline is "async mode + 4× download growth + still 20 KB".

## Non-Goals (deferred to 0.6.0+)

- Message templating engine
- Stdin / message collectors
- Webhook-to-Telegram bridge
- `aiofiles` for non-blocking file uploads (sync `open()` is fast enough for sub-50 MB files; gold-plating)
- Streaming responses
- Trio / AnyIO support beyond what `asyncio` + `httpx.AsyncClient` give for free
- Type stubs / `py.typed` marker / full mypy typing pass
- A unified `Pingram` that detects async context — explicitly rejected during brainstorming as magical and IDE-hostile

## Architecture

### Module layout

```
src/pingram/
├── __init__.py        # re-exports Pingram + AsyncPingram + exception types
├── pingram.py         # existing sync Pingram (unchanged)
├── async_pingram.py   # NEW — AsyncPingram class (~150 lines)
├── _errors.py         # existing exception hierarchy (unchanged)
└── _retry.py          # extend with execute_with_retry_async
```

- `AsyncPingram` lives in its own file. Keeps each module focused on one class; avoids growing `pingram.py` past 300 lines.
- The same exception types serve both classes. `TelegramAPIError`, `RateLimitError`, `TransportError`, `PingramError` are reused as-is. Caller code that already handles them continues to work in both worlds.

### `AsyncPingram` class

Signature mirrors `Pingram` exactly:

```python
class AsyncPingram:
    def __init__(
        self,
        token: str,
        *,
        retries: int = 3,
        raise_on_error: bool = False,
        timeout: float = 10.0,
    ) -> None: ...

    async def me(self, **kwargs: Any) -> httpx.Response: ...
    async def message(self, chat_id: str | int, text: str, **kwargs: Any) -> httpx.Response: ...
    async def send_photo(self, chat_id, path, caption=None, **kwargs) -> httpx.Response: ...
    async def send_doc(self, chat_id, path, caption=None, **kwargs) -> httpx.Response: ...
    async def send_audio(self, chat_id, path, **kwargs) -> httpx.Response: ...
    async def send_video(self, chat_id, path, **kwargs) -> httpx.Response: ...

    async def aclose(self) -> None: ...
    async def __aenter__(self) -> "AsyncPingram": return self
    async def __aexit__(self, *exc_info) -> None: await self.aclose()
```

Internally:
- Holds an `httpx.AsyncClient` bound to `self._timeout`.
- Each public method delegates to a private `await self._execute_async(...)` that calls `execute_with_retry_async` and translates the result/error per `raise_on_error`.
- Per-call kwargs `_raise` and `_retries` are popped via the same `_pop_meta` helper as the sync side (functionally identical body — pure dict pops, no async machinery needed).

### Three supported usage shapes

```python
# 1. Context-manager (recommended — guarantees client cleanup)
async with AsyncPingram(token="...") as bot:
    await bot.message(chat_id="123", text="hi")

# 2. Manual lifecycle (matches how Pingram is used today)
bot = AsyncPingram(token="...")
try:
    await bot.message(chat_id="123", text="hi")
finally:
    await bot.aclose()

# 3. Fire-and-forget (allowed but discouraged)
bot = AsyncPingram(token="...")
await bot.message(chat_id="123", text="hi")
# httpx.AsyncClient is GC'd eventually; emits a resource-warning
```

Shape 3 is documented as discouraged but not broken. The README will lead with shape 1.

### Async retry executor

New top-level function alongside `execute_with_retry` in `_retry.py`:

```python
async def execute_with_retry_async(
    request_fn: Callable[[], Awaitable[httpx.Response]],
    *,
    retries: int = 3,
) -> httpx.Response: ...
```

Same policy, line-for-line, as the sync executor:

| Condition | Behaviour |
|---|---|
| 2xx / 3xx | Return immediately |
| 400, 401, 403, 404 | Fail-fast — no retry |
| 429 | Honour `parameters.retry_after`, else exponential backoff |
| 5xx | Exponential backoff with jitter |
| `ConnectError` / `ReadTimeout` / `WriteTimeout` / `PoolTimeout` / `RemoteProtocolError` | Backoff and retry; re-raise after exhaustion |

Two differences from the sync version:
1. `await request_fn()` instead of `request_fn()`
2. `await asyncio.sleep(...)` instead of `time.sleep(...)`

Test-injection hook mirrors the sync side: tests patch `pingram._retry.asyncio.sleep` to make the async suite instant. The existing `mock_sleep` fixture is extended to patch both `time.sleep` and `asyncio.sleep` in one go.

**Duplicate rather than abstract.** Two ~30-line executors are easier to read and modify than one 50-line generic that branches on `iscoroutinefunction`. httpx itself ships parallel sync/async implementations for exactly this reason. Reconsider if a third client (e.g. Trio) ever lands.

### Behaviour matrix (identical to sync)

| `raise_on_error` | Success | Telegram error after retries | Transport error after retries |
|---|---|---|---|
| `False` (default) | returns `httpx.Response` | returns failed `httpx.Response` | re-raises `httpx.RequestError` |
| `True` | returns `httpx.Response` | raises `TelegramAPIError` / `RateLimitError` | raises `TransportError` (wraps original as `__cause__`) |

### Public API surface

`__init__.py` adds one export:

```python
from pingram.async_pingram import AsyncPingram

__all__ = [
    "Pingram",
    "AsyncPingram",
    "PingramError",
    "TransportError",
    "TelegramAPIError",
    "RateLimitError",
]
```

```

├── test_send_photo.py              # unchanged
├── test_send_doc.py                # unchanged
├── test_send_audio.py              # unchanged
├── test_send_video.py              # unchanged
├── test_async_get_me.py            # NEW — incl. async with lifecycle test
├── test_async_send_message.py      # NEW
├── test_async_send_photo.py        # NEW
├── test_async_send_doc.py          # NEW
├── test_async_send_audio.py        # NEW
└── test_async_send_video.py        # NEW
```

Async test coverage targets mirror the sync 0.4.0 coverage:

- `me()`: success, retries-on-503, retries=0 no-retry, `raise_on_error=True` raises `TelegramAPIError` and `RateLimitError`, transport-error wrapping, naked httpx propagation, `_raise` per-call override, **and** `async with` lifecycle test verifying `aclose` is called.
- `message()`: chat_id + text forwarding, extra-kwargs as form data, underscore-kwarg stripping, per-call raise override.
- Media (photo / doc / audio / video): URL path + local-file multipart path.

**Configuration:**

```toml
[tool.pytest.ini_options]
testpaths = ["tests/unit"]
asyncio_mode = "auto"
markers = [
    "integration: real-API tests; require BOT_TOKEN + CHAT_ID env vars",
]
```

`asyncio_mode = "auto"` makes every `async def` test function automatically run under the asyncio event loop without per-function `@pytest.mark.asyncio`.

Add 6 async siblings to `tests/integration/` mirroring the existing sync integration tests so the Integration workflow exercises both clients on every push to main. Marked with `@pytest.mark.integration`. In scope for 0.5.0.

Estimated test growth: 38 → ~80 unit tests, 6 → 12 integration tests.

## Risk assessment

| Risk | Likelihood | Mitigation |
|---|---|---|
| Sync `Pingram` regresses because shared kwarg-pop helper changes | Low | Sync class unchanged in this release; helper logic remains pure dict ops, no async machinery |
| `respx` async mocking breaks edge cases | Low | respx documents full async parity; current `mock_api` fixture works for both transports |
| `pytest-asyncio` config conflicts with existing sync tests | Low | `asyncio_mode = "auto"` only activates for `async def` tests; sync tests untouched |
| Users mix sync and async clients in same code, get confused | Low-medium | README leads with `async with` shape; class name `AsyncPingram` makes intent explicit |
| Local-file uploads block the event loop noticeably | Low | Sub-50 MB Telegram limit; reads take milliseconds. Revisit with `aiofiles` only if anyone reports a problem |
| Async tests too flaky on slow CI runners | Low | `mock_sleep` patches `asyncio.sleep` to a no-op — tests are deterministic, no real time elapses |

## Success criteria

- `pip install pingram==0.5.0` succeeds on Python 3.9, 3.10, 3.11, 3.12, 3.13 from a clean environment
- Existing 0.4.0 sync code runs unchanged against 0.5.0 (verified manually + via existing integration suite)
- `from pingram import AsyncPingram` works
- `async with AsyncPingram(...) as bot: await bot.message(...)` works end-to-end against the real Telegram API
- README displays a green CI badge with async tests included
- 0.5.0 ships via tag push without manual `twine upload`
- At least three user-visible improvements over 0.4.0: `AsyncPingram`, `async with` lifecycle, full sync-parity async methods
